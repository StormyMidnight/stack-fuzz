# AFL++ Stack Fuzzing Experiment: Exception Safety vs. Undefined Behavior

This project evaluates how coverage-guided fuzzing (AFL++) behaves when targeting stateful data structures under different exception and memory safety paradigms. 

Using a fixed-capacity C++ stack (`FixedStack`) and an unguarded `std::stack` wrapper, this experiment contrasts how fuzzers handle **explicit, caught C++ exceptions** versus **implicit undefined behavior (UB)**—and highlights the critical role AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan) play in detecting non-crashing memory faults.

---

## Key Objectives & Insights

1. **Stateful Fuzzing Dynamics:** Stacks require precise sequence ordering (e.g., $N$ consecutive pushes) to hit boundary conditions. We analyze AFL++’s ability to discover these state sequences via seed mutation vs. random search.
2. **Exception Safety vs. Undefined Behavior:**
   * `FixedStack` manages bounds explicitly via C++ exceptions (`StackFullException`, `StackEmptyException`). Under fuzzing, high coverage with **zero crashes** represents a successful safety verification.
   * `std::stack` used without bounds checking exhibits undefined behavior on empty `pop()`/`top()` operations.
3. **The Sanitizer Dependency:** Undefined behavior does not inherently trigger process crashes (`SIGSEGV`/`SIGABRT`). Without sanitizers, an optimized binary may execute invalid reads/writes silently, leading to **false-negative "zero crash" fuzzing results**.
4. **Memory Boundaries & Redzones:** Early iterations of `FixedStack` placed storage inline inside a `std::array`, which allowed off-by-one errors to corrupt adjacent struct members without tripping ASan. Shifting to a heap allocation (`std::unique_ptr<T[]>`) ensured ASan redzones explicitly caught out-of-bounds accesses—demonstrating that **sanitizer effectiveness depends directly on memory allocation boundaries**.

## Repository Layout

| Directory / File | Description |
| :--- | :--- |
| **`include/mystack.hpp`** | `FixedStack<T, Capacity>` implementation with explicit exception handling. Compiling with `-DINJECT_BUG` introduces a deliberate off-by-one heap overflow for positive-control testing. |
| **`include/stl_stack_wrapper.hpp`** | `std::stack<int>` wrapper representing unguarded/naive usage (no empty checks before `pop()` or `top()`). |
| **`harness/*_fuzz.cpp`** | AFL++ stdin fuzz targets sharing an identical 1-byte op-code encoding scheme for parity: <br>• `byte % 4 == 0` $\rightarrow$ `pop()` <br>• `byte % 4 == 1` $\rightarrow$ `top()` <br>• `byte % 4 == 2 or 3` $\rightarrow$ `push(byte)` |
| **`corpus/`, `corpus_stl/`** | Identical seed suites (balanced ops, alternations, 16-element overflows, empty pop/top). |
| **`analysis/`** | Python metrics scripts (`analyze_afl.py`, `visualize_stacks.py`) to parse AFL results, plot path discovery, deduplicate crash traces, and reconstruct execution depth. |
| **`tools/stack_trace.cpp`** | CLI utility to replay and inspect the exact stateful operations generated by any fuzzing testcase. |

## Getting Started

### Prerequisites

* C++20 compatible compiler (`g++` or `clang++`)
* `make`
* **Optional (for fuzzing campaigns):** [AFL++](https://github.com/AFLplusplus/AFLplusplus) installed locally (`afl-clang-fast++` on your `PATH`).

### Building

The project `Makefile` supports four distinct build configurations:

```bash
# 1. Plain Build (Standard compilation without sanitizers or AFL instrumentation)
make plain

# 2. Sanitizer Validation (ASan + UBSan enabled, no AFL instrumentation; for manual checking)
make asan

# 3. AFL++ Instrumented (AFL++ compiler without sanitizers)
make afl

# 4. AFL++ + ASan/UBSan (Recommended target for fuzzing campaigns)
make afl-asan
```
**Note on Flags:** Sanitizer targets include `-fno-sanitize-recover=all`. This ensures that detected faults immediately terminate the process (`exit 1`) so AFL++ can capture UB as a crash.

---

## Running Fuzzing Campaigns

To execute comparable campaigns, run both targets for an equal duration (e.g., 30–60 minutes):

```bash
# Campaign A: Exception-Safe FixedStack (Expected result: 0 crashes)
afl-fuzz -i corpus -o out_mystack -- ./build/mystack_afl_asan

# Campaign B: Unguarded STL Stack (Expected result: Rapid UB crashes)
afl-fuzz -i corpus_stl -o out_stlstack -- ./build/stlstack_afl_asan

# Baseline Sanity Check: Planted Bug Verification
afl-fuzz -i corpus -o out_mystack_buggy -- ./build/mystack_buggy_afl_asan
```
Crashing inputs will be captured in `out_*/default/crashes/`.

## Results & Analysis Tools

### 1. Generating Full Performance Reports

The analysis pipeline processes `fuzzer_stats` and `plot_data` while deduplicating crashes by replaying inputs against binaries to group by unique sanitizer stack traces:

```bash
# Install optional plotting dependencies
pip install -r analysis/requirements.txt

# Run comparative analysis
python3 analysis/analyze_afl.py \
    --run mystack=out_mystack \
    --run stlstack=out_stlstack \
    --run mystack_buggy=out_mystack_buggy \
    --binary mystack=build/mystack_afl_asan \
    --binary stlstack=build/stlstack_afl_asan \
    --binary mystack_buggy=build/mystack_buggy_afl_asan \
    --out analysis_report
```
**Generated Outputs (`analysis_report/`):**

* `report.md` — Complete analytical write-up (execs/sec, time-to-first-crash, unique signature counts).
* `comparison.csv` — Summary spreadsheet.
* `<run>_signatures.csv` — Individual crash signature groups.
* Visualizations (`.png`) for execution speed, corpus growth, and unique bug rates over time.

### 2. Inspecting Reconstructed Stack States

To inspect the exact stack sequences AFL++ constructed from raw bytes:

```bash
# Build visualizer tools
make tools

# Trace a single generated testcase or crash input
./build/stack_trace --target mystack --file corpus/seed_overflow

# Analyze state space distribution across an entire AFL queue
python3 analysis/visualize_stacks.py --target mystack \
    --tool build/stack_trace --dir out_mystack/default/queue --stats-only
```
